## Findings considered and rejected

- **Port `verifyFlueProviderSurface`'s exact-version pinning** (reference
  `model-auth.ts:52-60`): rejected — a reusable package expresses its version
  contract through the peer range, not hardcoded version equality; the
  `pi-ai/compat` catalog probes it relies on are also a module-identity trap.
- **Reject `OPENAI_API_KEY` in the host env by default** (reference behavior):
  rejected as a default — generic hosts may legitimately run the plain
  `openai` provider alongside Codex. Hosts can add it via `rejectedEnvNames`.
- **SQLite-sidecar path checks** (`-wal`/`-shm`, reference
  `codex-subscription-auth.ts:247-251`): folded into the generic
  `forbiddenPaths` option instead of a special case.
- **Config-file lookup in the login CLI** (mario.config.json): rejected —
  hosts pass `--auth-path` or `FLUE_CODEX_AUTH_PATH`; a generic package should
  not invent a config file format.
- **Publishing a Flue blueprint kind**: not currently possible — `flue add`
  kinds are sandbox/channel/database/tooling with a fixed known-blueprint
  list; the URL form (`flue add tooling <repo-url>`) is the supported path
  and is documented in Plan 004.
- **A scaffolding command** (`create-flue-codex-app` / `init` subcommand):
  rejected — Flue owns project creation (`flue init`) and integration
  (`flue add`); a per-package scaffolder would compete with the framework and
  rot with every beta. The framework-native story is `flue init` →
  `pnpm add flue-codex-oauth` → `npx flue-codex-login`, and Plan 005's
  verified example covers the "show me a working app" need.
